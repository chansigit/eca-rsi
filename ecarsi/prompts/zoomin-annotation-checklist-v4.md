## Required order (the host checks each step; a submission made earlier is rejected and costs a turn)
The prompt above already lists this lineage's evidence files, its UMAP figures, the pending type clusters and every 2.0 cluster with its type intersections; list_evidence and annotation_status only repeat them.
1. One batched turn: read_evidence on a UMAP png listed above, check_qc_scores, and deg_lookup (or one bounded deg_sql) for the clusters you will label.
2. submit_types with exactly the pending type clusters listed above. Every entry is action keep with a coarse_label from this lineage's own labels: submit_types only assigns identity, so a cluster that belongs to another lineage or should be removed is still keep here (nearest own label) and is moved or removed in submit_quality.
3. submit_quality with one entry per 2.0 cluster; each of that cluster's type intersections exactly once (listed above with cell counts). A removal is {"type_clusters": [...], "action": "remove", "remove_reason": one of doublet, low-quality, ambient, stress, dissociation, dying, batch, other, "confidence": ..., "evidence": ..., "rationale": ...}; a reassignment is {"type_clusters": [...], "action": "reassign", "reassign_to": a coarse label of another lineage, "fine_label": ..., "confidence": ..., "evidence": ..., "rationale": ...}; everything else is keep.
An accepted submit_quality completes the session; there is no finalize step.
Label rules (host-enforced): keep needs a coarse_label from this lineage's own labels (the prompt lists them as Lineage labels). Reassignment exists only in submit_quality and only to a label listed under Other permitted labels; when that list is empty, keep or remove. remove without remove_reason is rejected. Clusters that are one population share one fine_label and are joined with merge_target; every cluster in a merge group carries the identical coarse_label and fine_label; clusters that are different populations need different fine labels; one fine label belongs to exactly one coarse label.
proposal_json may be passed as the JSON object itself. A rejection names the exact missing items: fix only those and resubmit; do not restart the reads.
