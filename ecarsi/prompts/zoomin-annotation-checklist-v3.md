## Required order (the host checks each step; a submission made earlier is rejected and costs a turn)
1. In one turn: list_evidence with offset 0 and offset 30 (pages hold 30 paths; a page past the end is empty) and annotation_status for offsets 0, 10, 20, ... up to the number of 2.0 clusters (pages hold 10 entries). Then in one batched turn: read_evidence on the lineage UMAP png it lists, check_qc_scores, and deg_lookup for the clusters you will label.
2. submit_types with exactly the pending type_scope clusters (annotation_status shows type_scope). Every entry is action keep with a coarse_label from this lineage's own labels: submit_types only assigns identity, so a cluster that belongs to another lineage or should be removed is still keep here (nearest own label) and is moved or removed in submit_quality.
3. submit_quality with one entry per 2.0 cluster; each of that cluster's type intersections exactly once (annotation_status pages list them). A removal is {"type_clusters": [...], "action": "remove", "remove_reason": one of doublet, low-quality, ambient, stress, dissociation, dying, batch, other, "confidence": ..., "evidence": ..., "rationale": ...}; a reassignment is {"type_clusters": [...], "action": "reassign", "reassign_to": a coarse label of another lineage, "fine_label": ..., "confidence": ..., "evidence": ..., "rationale": ...}; everything else is keep.
4. finalize_annotation.
Label rules (host-enforced): keep needs a coarse_label from this lineage's own labels (the prompt lists them as Lineage labels). Reassignment exists only in submit_quality and only to a label listed under Other permitted labels; when that list is empty, keep or remove. remove without remove_reason is rejected. Clusters that are one population share one fine_label and are joined with merge_target; every cluster in a merge group carries the identical coarse_label and fine_label; clusters that are different populations need different fine labels; one fine label belongs to exactly one coarse label.
proposal_json may be passed as the JSON object itself. A rejection names the exact missing items: fix only those and resubmit; do not restart the reads.
