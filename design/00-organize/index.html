Organize：分离程序执行与模型推理

类型说明：「模型推理」指调用语言模型进行规划、判断或注释；「程序执行」指按代码完成数值计算、校验、查询、读写和结果应用，可使用 CPU 或 GPU。模型发起的工具调用仍属于程序执行；这些标注不增加调度步骤。

目的：一个数据集等待 模型 时，其他数据集的计算继续进入 pool。程序执行内部连续执行，不把校验、日志、文件写出各自变成调度任务。

设计草案，尚未实现或部署。Organize 通常在 round 1 之前执行，同时确定 analysis units 和完整实验样本的映射，在写出前检查二者兼容；不执行 QC、聚类或细胞删除。

已确认：实验划分与完整性检查统一交给 Organize。Per-sample 信任并执行 Organize 的确认结果，不再让 模型 重新划分或审核实验样本。

细胞排除记账〔程序执行〕

Organize 执行后按来源 cell IDs 对账：默认全部分配；若执行已授权的来源/细胞排除，逐细胞保存原因与决定引用。拆分、合并和改名只记录映射，不算删除；未被计划覆盖的细胞是错误。上游已有账本继续引用，缺失历史记录需明确标注。

每次过滤 → 记录 cell IDs、原因和证据 → 与输出一起保存并核对细胞守恒。这是步骤内的必做环节，不新增排队任务。无排除也记录零排除摘要；账本未通过验收，该步不能完成。详见 统一细胞排除账本。

只分三个执行块

① 准备输入证据〔程序执行〕 → ② 组织计划〔模型推理〕 → ③ 执行组织计划〔程序执行〕 → per-sample

执行块类型输入 → 输出块内连续完成的工作执行位置
① 准备输入证据
organize.prepare		程序执行已标准化来源文件及上游记录 → 紧凑 metadata 摘要、来源版本和校验记录发现来源；验证 ECA-PP 输出和 counts；解析上游列证据；同时整理器官、实验/文库信息和用户显式样本声明；统计 metadata；记录输入身份。尽量复用读取结果，摘要保存后关闭文件、释放矩阵与计算资源。Scheduler 分配资源；Worker 执行
② 组织计划
organize.plan		模型推理摘要、组织规则、已有样本声明 → 组织计划与实验映射候选模型结合器官和实验/文库证据，明确实验划分依据，再制定兼容的合并、拆分计划。优先复用有效映射或用户显式声明；Coordinator 校验结构、来源引用、过滤条件和物种约束。需要扫描数据的完整性审计在③开头完成，通过后才最终接受计划与映射。Agent Bridge 调用模型；Work Coordinator 校验并推进
③ 执行组织计划
organize.execute		程序执行固定版本的来源文件、计划和实验映射 → organized.h5ad、manifest、确认的实验映射及来源证据写出前先检查细胞守恒、映射覆盖与实验完整性，确保同一个确认实验没有被分到多个 analysis unit；冲突交回②修正。通过后接受计划与映射，再分割、合并、保存来源信息、写出、回读并记录完成结果。所有这些动作都在同一个计算块内顺序完成。Scheduler 分配资源；Worker 执行；Coordinator 验收结果

三个名称表示可恢复的执行边界，不是三个新服务。② 不占计算 Worker 名额；小型校验直接在 Coordinator 中执行，需要扫描 obs 或矩阵的分配与实验完整性审计放在③开头，仍是块内检查，不增加调度任务。

真正需要等待的地方

  • ①的摘要准备好，②才能调用模型。①结束后不保留完整矩阵等待回复。
  • ②有通过初步校验的计划和实验映射，③才能开始审计；完整审计通过后才能写出。已有有效计划与映射可跳过模型推理，仅执行程序校验；显式计划仍须包含或补齐实验映射，并通过同样的校验。
  • ③必须先确认每个已接受来源的细胞恰好分配一次，再开始写出。不能因 filters 漏细胞、重复分配或漏来源，也不能把同一个确认实验拆散后分别做 OSP。
  • ③的审计若发现计划有问题，将具体错误交回②修正；该计算块退出并释放资源，不能原地占着 Worker 等 模型。资源或磁盘故障则按故障恢复，不让模型重新猜计划。
  • 产物、manifest、确认的实验映射及来源证据完整验收后，交给 per-sample 直接使用。batch_key_hint 仍只是批次校正建议；实验映射是独立的正式交付结果。

交给 per-sample 的结果

Organize 保存每个细胞的原始来源与 cell ID、确认的 sample ID、所属 analysis unit、实验划分依据，以及对应输入/计划版本。合并跨来源实验时保留证据；来源不明确应在 Organize 内解决或报告，不能把不确定结果转交下游再猜。

Per-sample 只检查收到的文件、版本和 cell IDs 是否与确认映射一致，然后准备子集并跑 OSP。它不重新调用 模型、不重新推断实验边界，也不重复审查 Organize 的组织理由。文件缺失、被修改或映射损坏属于交接错误，需报告修复，不是重新裁决 Organize。

什么时候才进一步拆？

默认不拆。多个独立 analysis unit 足够大、并行收益明确且不会造成大量重复读取时，才考虑按 unit 分发③。规模小就一个任务顺序完成。不要先为尚未证实的收益增加调度和中间文件。

①→②→③意味着必要时要跨 模型 边界再次读取输入，这是释放矩阵和计算资源的代价；可复用磁盘缓存，但不为等待模型常驻一个大内存进程。应测量整体吞吐与重复 I/O，而不是追求更多任务数。

恢复边界

情况恢复方式
准备完成后中断输入版本不变时复用准备摘要与校验记录，不重新规划数据范围。
等待模型时中断恢复持久交互；已有回复或已接受计划先复用，不无条件重复请求。
执行到一半 Worker 退出复用已验收 unit，重跑尚未完成的部分；允许重做未持久化的块内动作，不强制每个函数都存检查点。
结果写完但通知丢失先核对输出及收据，再推进下游；不直接重新计算。

哪个组件负责？

  • Work Coordinator：管理这三个块的依赖、组织计划与实验映射的接受、恢复和下游推进。
  • Agent Bridge：管理②的模型请求、并发、分流及回复持久化。
  • Warm Pool Scheduler：给①和③分配已有资源。
  • Warm Pool Worker：执行①和③的固定代码。校验、日志和保存收据是块内职责。

复用哪些现有代码？

①复用 ecarsi/upstream.py 的发现、校验与来源证据解析，以及 ecarsi/organize.py:profile_unit；②复用 ecarsi/plan.py；③复用 ecarsi/execute.py:execute_plan。另将现有 ecarsi/sample_mapping.py 和 ecarsi/persample.py 中的实验识别与完整性检查迁入 Organize 的三个块内，不新增独立服务或执行块。这是拟议职责调整，尚未修改执行代码。

实现重点是解除这三块之间的进程和内存绑定，保存必要的交接结果；不是重写原有科学计算，也不是把每个内部函数变成独立任务。
